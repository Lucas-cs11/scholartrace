# 分支策略（GitHub Flow）

P0 门禁项「分支策略文档化」。采用 **GitHub Flow**：`main` 始终处于可发布状态，
改动经短生命周期分支 + PR 合入。单人开发同样适用，并为将来多人协作留好接口。

## 分支

| 分支 | 用途 | 生命周期 |
|------|------|---------|
| `main` | 唯一长期分支，始终可发布 | 永久 |
| `feat/<主题>` | 新功能 | 合入即删 |
| `fix/<主题>` | 缺陷修复 | 合入即删 |
| `chore/<主题>` | 工程 / 构建 / 文档改动 | 合入即删 |
| `p<N>/<主题>` | 生产化某阶段内的成块工作，如 `p0/dockerfile` | 阶段结束即删 |

命名用小写短横线：`feat/local-recall-index`、`fix/history-user-scope`。

## 流程

1. 从 `main` 切出短命分支
2. 在分支上提交 —— 提交信息写**为什么**，不写做了什么
3. 推送并开 PR，**CI 全绿**方可合并
4. 合并（squash）后删除分支，`main` 保持可发布

## 门禁

- 改动经 PR 进入 `main`。紧急修复可直推，但事后须补 issue 记录
- PR 合并前 `.github/workflows/ci.yml` 必须通过
- **阶段门禁（总纲 §7）未过时，不得把下一阶段的改动并入 `main`**

## 强制程度（当前状态）

约定按上述执行，但**单人开发期未启用强制 ruleset** —— 直推 `main` 技术上仍可行，
仅供紧急修复使用。

**引入第二名协作者之前必须启用分支保护**（要求 PR + CI 通过 + 禁止强推 + 禁止删除 `main`）。
