## 1. 目标与约束

### 1.1 目标状态

面向**正式公测（千人以上）**的学术检索与研究助手服务，具备：可承载的并发、可观测的运行状态、
可控制的成本、可回滚的发布流程、可辩护的数据合规。

### 1.2 已确定的技术决策

| 决策项 | 选择 | 依据 |
|--------|------|------|
| 引擎与评测语言 | **保持 Python** | ① 工作负载 I/O 密集，语言非瓶颈；② `scripts/` 12,230 行 + `tests/` 2,439 行评测体系是核心资产，换栈即毁掉证据链 |
| 前端语言 | **转 TypeScript** | 原生 JS 无构建、无类型，撑不住筛选/详情/会话/SSE 的产品化需求 |
| 检索索引 | **Postgres 单库**（`tsvector`/`pg_search` + `pgvector`） | 2 vCPU / 7.6 GB 硬件下 OpenSearch 不可行；且省掉一整套独立基础设施 |
| 语料策略 | **不 fork 全量**：API 分页拉子集 + 懒加载增量 | 300 GB 卷约束；全量 TB 级对个人项目不成比例 |
| 产品形态 | 研究助手（多轮对话），排在 P4，**可裁剪** | 用户选择；排后以便必要时降级为首发只做检索工具 |
| 前端部署 | React + Vite + TS，自托管 | DEEP 单次 30–60 s，serverless 执行时限不兼容 |
| 推进方式 | **串行为主 + 一次有意并行** | 单人开发，真并行不成立；P2 导入等待期用于写 P1 |

### 1.3 环境事实（已实测）

| 项 | 实测值 | 影响 |
|----|--------|------|
| **CPU** | **2 vCPU** | 并发上限的硬约束 |
| **内存** | **7.6 GB**（已用 2.3 GB） | ⚠️ **比磁盘更紧的约束**；决定 Postgres 单库路线 |
| 根盘 `/` | 6.7 GB，**可用 2.1 GB** | ⚠️ 只放 OS；Docker data-root 等必须外迁 |
| `/mnt/data` | 100 GB（代码树，已用 17 GB） | 代码与评测数据留此 |
| `/mnt/scholartrace` | **295 GB**（新增，可用 292 GB） | 全部重数据 |
| Docker | **未安装** | P0 安装并将 data-root 指向数据卷 |
| 版本控制 | **无 git 仓库** | ⚠️ P0 首要项：无 VCS = 无回滚、无分支、无 CI |
| Python | 3.14.4 | 注意部分依赖对 3.14 的兼容性 |
| Node | 20.20.2 | 满足 React + Vite |

### 1.4 人力约束

**单人开发，约 12 小时/天。** 这决定了：
- 子项目无法真并行，阶段基本串行
- 上下文切换有真实损耗，排期须预留缓冲
- **任何「运维负担重」的方案都应被拒绝**——运维时间直接吃掉开发时间

## 3. 目标架构

```
┌─ 浏览器 ── React + Vite + TS ────────────────────────┐
│   检索 / 筛选 / 详情 / 会话追问 / 真实进度(SSE)        │
└──────────────────────┬───────────────────────────────┘
                       │ HTTPS · SSE
┌──────────────────────▼───────────────────────────────┐
│  反向代理（Caddy 或 Nginx）                            │
│  TLS 终止 · 静态资源 · SSE 透传 · 基础限流              │
└──────────────────────┬───────────────────────────────┘
┌──────────────────────▼───────────────────────────────┐
│  FastAPI 服务层                                       │
│  ├─ 中间件：鉴权 · 限流 · 配额 · 成本上限 · 请求追踪     │
│  ├─ 会话与任务：异步队列 · 长请求 · 取消 · SSE          │
│  └─ 检索引擎（Python，保持不动）                        │
│       ├─ 本地召回：Postgres 全文/BM25 索引              │
│       ├─ 远程召回：OpenAlex API（按量计费）             │
│       └─ 精排：LLM Reranker                            │
└──────────────────────┬───────────────────────────────┘
┌──────────────────────▼───────────────────────────────┐
│  Postgres — 关系数据 + 全文索引 + pgvector             │
│  Redis    — 缓存 / 限流计数 / 任务队列                  │
└──────────────────────────────────────────────────────┘
```

### 3.1 与现状的关键差异

1. **检索引擎从「只有 OpenAlex API」变为「本地优先 + 远程兜底」**
2. **从无状态变为有状态**（会话）
3. **从同步长请求变为异步任务 + SSE**
4. **从零基础设施变为 Postgres + Redis 两件套**（刻意只加两件）

### 3.2 OpenAlex 成本模型（2026-02 起生效）

| 调用类型 | 单价 | 用途 |
|---------|------|------|
| 单篇查询（ID/DOI） | **免费，无上限** | 元数据补全 |
| 列表 / 过滤 `filter` | ~$0.0001 | **子集拉取主力** |
| 检索 `search` | ~$0.001 | 召回主路径 |
| S3 全量快照 | **免费** | 备用，下载后即删 |

免费额度：每 key 约 **$1/天** ≈ 1,000 次 search ≈ 100 次检索/天。

**架构含义**：优先用 `filter` 与单篇查询替代 `search`；懒加载索引吸收重复查询以压低 `search` 调用量。

## 5. 阶段、排期与门禁

> **各阶段周期相加 = 16–25 周**（P0 1–2 + P1 3–4 + P2 4–6 + P3 2–4 + P4 4–6 + P5 2–3）。
> **计入单人开发的上下文切换损耗（约 +20%），总周期估计 20–28 周。**
> 每阶段 = `实现 → 单元测试 → 集成测试 → 联调 → 阶段验收(gate)`。
> **门禁不绿，不进入下一阶段。**

### P0 — 工程底座（1–2 周）

**内容**：git 初始化与分支策略 · Docker 安装且 data-root 迁至 `/mnt/scholartrace/docker` ·
Dockerfile + compose · CI（构建 + 测试）· dev/staging/prod 分层 · 密钥管理（`.env` 移出代码树）·
`.env.bak` 清理 · 现有 97 单测接入 CI

**门禁**：
- [ ] `git log` 有历史，分支策略文档化
- [ ] 镜像可重复构建（同 commit 两次构建产物一致）
- [ ] 三个环境均可部署
- [ ] **97 个单测在 CI 中全绿**
- [ ] 仓库内无任何密钥（含 `.env.bak`）

---

### P1 — 服务化骨架（3–4 周）

**内容**：S1 网关 + S2 可观测性 + S3 存储（三者耦合紧，同期做）
- 账号、鉴权、限流（用户级 + 全局级）、配额、**每日成本上限**
- 结构化日志、指标（QPS / P99 / 错误率 / token 成本 / 各上游命中率）、告警
- Postgres schema（用户 / 会话 / 历史 / 反馈）+ 迁移工具 + Redis
- **修静默降级**：区分「确实无结果」与「上游不可用」，后者返回明确错误
- **修 `/history` 越权**：加用户维度
- 真实健康检查：拆分 liveness / readiness，探测 Postgres、Redis、LLM、OpenAlex

**门禁**：
- [ ] 鉴权 / 限流 / 配额 / 成本上限：单元 + 集成测试全绿
- [ ] 可观测性**联调**：真实请求能在看板上看到端到端链路与成本
- [ ] 依赖故障注入：Postgres / LLM / OpenAlex 各自不可用时，`/health` 正确报不健康，`/search` 返回明确错误而非空结果
- [ ] **灰度冒烟：50 人可正常使用**

---

### P2 — 检索能力重建（4–6 周）⭐ 含关键决策点

> **本阶段以「测量」开头，而不是以「建设」开头。**

**P2.0 测量先行（约 1 周，成本约 $1）**
用 `filter` 分页拉 100–300 万篇目标子集 → 建 Postgres 全文索引 →
**用现有 eval harness 跑 A/B：本地召回 vs OpenAlex API 召回，对比 F1**

**🚦 决策门禁**：只有当实测 F1 显著优于现状，才继续 P2.1。
若否则停止本阶段，把资源转向 P3——**不要为了沉没成本继续建设。**

**P2.1 索引服务化**：语料流水线 · 增量更新 · 筛选项（年份/venue/被引/OA）
**P2.2 懒加载索引**：每次检索结果回写本地索引，使覆盖随使用增长
**P2.3 召回链路切换**：本地优先 + 远程兜底（前提 P2.0 通过）

**门禁**：
- [ ] **A/B F1 对比报告**（含 gold 覆盖率、延迟、成本三项）
- [ ] 索引服务压测：在 2 vCPU 上测出并发上限并记录
- [ ] 召回回归测试：现有 22 条冻结 query 全部结果可比对
- [ ] 容量重估：依据实测数据触发扩容决策（见 §8）

## 6. 测试策略

### 6.1 层级与责任

| 层级 | 范围 | 何时 | 通过标准 |
|------|------|------|---------|
| **单元测试** | 函数/类，mock 外部依赖 | 每次提交 | 全绿 + 覆盖率不下降 |
| **集成测试** | 模块间真实对接（Postgres/Redis 真实实例） | 每阶段 | 全绿 |
| **联调** | **跨服务真实对接，禁止 mock** | 每阶段末 | 端到端链路可观测且正确 |
| **系统/验收** | 完整用户路径 + 非功能属性 | 阶段门禁 & P5 | 门禁清单全绿 |

**「联调」的定义**：不是「跑通了单元测试」，而是**真实组件真实对接**——真实 Postgres、
真实 Redis、真实 OpenAlex、真实 LLM。历史上在线链路从未跑通，正是因为在 mock 上验证通过。

### 6.2 每阶段必须产出

1. 该阶段的测试代码（与实现同 PR）
2. **测试报告**：跑了什么、结果如何、有哪些已知未覆盖项
3. **门禁证据**：能证明门禁清单已满足的产物（日志、指标截图、报告文件）

### 6.3 测试资产复用

**`scripts/` 与 `tests/` 那 14,669 行是本计划的地基。**
P2 的 A/B 判定、P3 的回归验证、P5 的质量基线，全部复用现有 harness 与冻结 gold corpus。
**任何阶段都不得破坏评测体系的可复现性。**

### 6.4 P5 上线前完整测试清单

| # | 测试 | 内容 | 通过标准 |
|---|------|------|---------|
| 1 | **压力测试** | 逐步加压至拐点，测 QPS / P99 / 错误率 / 资源占用 | 定出容量上限并记录；拐点前无异常错误 |
| 2 | **混沌测试** | 杀索引 / 断 LLM / 断 Postgres / 断 Redis / 网络抖动 | **用户收到明确错误，而非「无结果」**；系统可自愈 |
| 3 | **端到端全链路** | 真实用户路径 × 全模式矩阵 × 多轮会话 | 全部通过 |
| 4 | **安全审计** | Prompt 注入、越权访问、配额绕过、密钥泄漏、依赖漏洞 | 无高危项 |
| 5 | **数据一致性** | 并发读写、事务边界、**备份恢复演练** | 恢复后数据完整可用 |
| 6 | **合规** | 隐私政策、ToS、数据保留与删除、摘要再分发版权 | 文档就位并通过自查 |
| 7 | **发布演练** | 灰度放量 → 监控观测 → **真实执行一次回滚** | 回滚在可接受时间内完成且数据无损 |
| 8 | **成本验证** | 单次检索成本、每用户日成本、月度总额 | 在预算内且可被限额强制约束 |

## 7. 门禁清单（Gate Checklist）

每次进入下一阶段前，逐项确认：


## 8. 容量与「先测量再扩容」

### 8.1 现有容量 vs 公测需求

| 资源 | 当前（开发验证期够用） | 千人公测所需（估） |
|------|----------------------|-------------------|
| 磁盘 | 295 GB 数据卷，P0–P5 预计用至 230 GB | **500 GB – 1 TB**（懒加载索引累积 + 用户数据 + 日志 + 备份） |
| 内存 | 7.6 GB | **≥ 32 GB**（Postgres + Redis + 应用 + 页缓存） |
| CPU | 2 vCPU | **≥ 8 vCPU** |

**当前机器是开发验证环境，不具备千人公测承载力。** 磁盘只是三项中的一项，
内存与 CPU 的缺口更紧迫——这不是上线当天应当才发现的事。

### 8.2 扩容门禁（贯穿全程）

**在 P2 结束时依据实测数据做一次正式的容量评估**，触发条件：

- 数据卷使用率 > 70%，或
- 压测显示 P99 超目标，或
- 内存导致 Postgres 频繁落盘

**P5 之前必须完成硬件升级。** 当前 2 vCPU / 7.6 GB 是开发验证环境，
**不具备千人公测承载力**——这一点不应在上线当天才发现。
